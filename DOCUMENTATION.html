JIRA TO BRANCH — BEFORE YOU OPEN A PR

Semantic Scout

On-demand pre-PR review for any AN or PIC ticket. Scout reads Jira (including comments), reads your git branch, and tells you what is done, what is missing, and what bots are likely to flag — before reviewers see the PR.

Cursor skill + MCP v5 universal Jira + git only ~5 min setup once

Product brief

Goal
Give the team an on-demand way to check that ticket work is actually on the branch before anyone opens a pull request.
Description
Semantic Scout is the delivery-truth layer for BI tickets. You point it at a Jira key and your feature branch. It builds a requirement list from the ticket, infers which files should change (dashboard, paginated report, semantic model), scores evidence in the diff, warns on scope creep, and surfaces bot-ahead items from squad history. It does not replace lakehouse SQL proof — pair with KPI Forge (numbers) and Fabric Validator when KPIs must match SQL.
Success looks like
  • Any ticket can be reviewed when needed — no pre-built JSON per ticket.
  • Every acceptance criterion gets a met / missing / manual line tied to files.
  • scout_ticket_review returns PASS-style clarity on delivery + branch hygiene.
  • BI devs run the flow from Cursor (skill + MCP) without one-off checklists in chat.
  • You complete the SCOUT RATING CARD, then choose A / B / C before the PR.
What we can achieve
  • Standardized pre-PR reviews instead of scattered “are we good?” threads.
  • Faster intake of new tickets — deliverable files inferred from the title and description.
  • Repeatable scope discipline (no surprise scripts/ or extra reports on the branch).
  • Bot comments predicted early from learned PR patterns.
What we can use it for
  • Pre-PR gate on every AN/PIC change.
  • Regression after DAX, RDL, or filter edits — “did we ship everything Jira asked for?”
  • New ticket kickoff — confirm scope and file list before you code.
  • Self-service review when reviewers are busy — you still own the final B decision.

Scout vs KPI Forge (simple split)

Semantic Scout

Question: Did I implement what Jira asked, on the right files, on this branch?

Inputs: Jira + git diff.

Output: Ratings, missings, bot-ahead, scope warnings.

KPI Forge

Question: Does lakehouse SQL match dashboard KPIs page by page?

Inputs: PBIR report + semantic model.

Output: SQL scaffolds + maturity score; numbers proven in Fabric.

Before vs after

Without Scout

PRs bounce for scope creep, half-done AC, or bot comments. Review cycles repeat. Paginated twins and docs get skipped.

With Scout

One card before the PR. Fix missings, clear bot-ahead, re-run. Reviewers start from a cleaner branch.

How it works

flowchart TD A["Semantic Scout for AN-XXXX"] --> B["Jira summary + description + comments"] B --> C["Infer deliverables .rdl / dashboard / .tmdl"] C --> D["Git diff vs main or Standard_dev"] D --> E["Rate requirements + branch + bot ahead"] E --> F{"A fix · B PR · C re-check"}

v5 is universal: no static ticket bundles, no Paginate runtime. MCP primary tool: scout_ticket_review. Health check: scout_engine_health.

Setup — once

  1. Clone glofoxinc/semantic_scout.
  2. In Cursor: Setup Semantic Scout
  3. Connect Atlassian + GitHub if asked; pip install -r scout/requirements.txt.
  4. Restart Cursor; run scout_engine_health — must show ok: true, version 5.0.0.
Done when you see the navy SEMANTIC SCOUT — BEFORE RAISING PR card on a real ticket.
