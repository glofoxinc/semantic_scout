BEFORE YOU CREATE A PULL REQUEST

Semantic Scout

You give your Jira ticket. Scout checks your Git branch against that ticket, then tells you what is done, what is still missing, and what to fix before you create the pull request.

Works in Cursor Setup ~ 5 minutes, once Saves ~ 15 to 30 min per ticket

What you will see

After you type Semantic Scout for AN-XXXX (your ticket), Scout returns one card. Here is what each part means in plain language.

On the cardIn simple words
Jira requirement rating How much of the Jira ticket is actually done in your files. 100 means every requested item is there. A low score means the ticket asked for work you have not put on the branch yet.
Branch rating How clean the branch is for a pull request. Extra files, a dashboard change with no matching paginated report, or a visual setting flipped by accident will pull this score down.
Combined + READY The overall call. READY YES means it is safe to create the pull request. READY NO means fix the listed items first.
Missings The ticket asked for these things. They are not in your branch. Example: Join Type is on the dashboard but not on the paginated report.
Suggestions (ahead) What to do next so reviewers and GitHub bots do not bounce the PR. Typical items: update the help / documentation page, keep the dashboard and paginated report in line, or fix something bots usually comment on.

Who this is for

Insights / Glofox analysts on AN or PIC tickets — dashboards, paginated reports, semantic models.

If you are about to create a pull request, run Scout first.

Before vs after

Without Scout

PRs bounce for extra files, missing ticket work, or GitHub bots. Reviewers spend 20–40 minutes. Often twice. Documentation and the paginated twin get forgotten.

With Scout

One card: ratings, missings, and suggestions. You fix, then raise. Bots are predicted from squad history, not guessed after the fact.

About 15 to 30 minutes back, each ticket

How it works

flowchart TD A["You: Semantic Scout for AN-XXXX"] --> B["Read Jira + all comments"] B --> C["Read the branch diff"] C --> D["Rate Jira vs branch"] D --> E["List missings"] E --> F["Suggest docs / dashboard / paginated / bots"] F --> G{"Your choice"} G -->|"A Fix first"| H["Apply fixes, then re-rate"] G -->|"B Raise PR"| I["PR may be opened"] G -->|"C Re-check"| J["You edit, run Scout again"]

Setup — once, about 5 minutes

You do not run install scripts. This is a Cursor skill.

  1. Open Cursor.
  2. In chat, type exactly
    Setup Semantic Scout
  3. If it asks for GitHub or Jira, answer once. That is all.
  4. Prove it works — type Semantic Scout for AN-XXXX with your real ticket.
You are done when you see a navy card titled SEMANTIC SCOUT — BEFORE RAISING PR, or Cursor asked for a login, you answered, and then the card appeared. If skills do not show, restart Cursor once and say Setup Semantic Scout again.

How repo and branch are found

You give only the Jira key (AN-XXXX or PIC-XXXX). You do not name the GitHub repo.

TicketRepo Scout selects

PIC with a client name in the titlematching glofoxinc/abc-customize-*

Then Scout looks for a branch whose name contains the ticket key (feature/<KEY>-* or <KEY>-*). Diff base is main, unless you asked for a promotion PR to Standard_dev. If no branch matches, Scout asks. It does not invent one.

Daily use

Before you raise a PR

Semantic Scout for AN-XXXX

Use your ticket. Scout uses the current branch.

After the card — reply with one letter

A
Fix first

Scout helps apply missings and bot items, then rates again.

B
Raise PR

You accept remaining risk. Only now may a PR be opened.

C
Re-check

You edit locally. Run Scout again when ready.

If a PR already exists

Semantic Scout on owner/repo#N for AN-XXXX
